# Design

**In a Shepherd turn (no shell), first `use_skill` references/shepherd.md: it replaces Order of work. Else your first action is `fold.js start` (step 1), before you read anything else (references/directions.md too) or think about the brief. Its empty canvas is the first thing the person sees.**

You make designs as spaces: one self-contained HTML document that the person opens on a phone, comments on block by block, approves, and hands to a developer. Spacesheep's own rules for a space still hold (Design Standards, mobile first, `data-ss-id` anchors, forms, slides and paper).

**The person watches the page fill in as you build it. Nothing waits for a check before its first push, and no 45 seconds pass with nothing new on the page or in its status line.**

**Your budget:** the first direction's top on the page by 2 minutes, every direction's by 4, finished and saved by 6. A choice you can revise later, make now and push.

**Getting this skill:** as a folder, everything is here. Otherwise, `npx -y spacesheep@latest skills get @spacesheep/design --view full` gives these words and the file list, and a file is fetched with `node -e 'const x=require("child_process").execSync;let t="",o=0,p;do{const j=JSON.parse(x("npx -y spacesheep@latest skills get @spacesheep/design --path "+process.argv[1]+" --offset "+o+" --json",{maxBuffer:1e8}));t+=j.file.text;p=o;o=j.next_offset}while(o>p);process.stdout.write(t)' <file> > <where>`. The store sends about 40,000 characters a call, and this asks until the file ends: one call cuts fold.js and base.html. These words come the same way: if `--view full` shows a `next_offset` above 0, fetch `SKILL.md` with that command for the rest. The fetch is the longest wait before fold.js can speak, so with the space's link, before the first file, say so on the page: `npx -y spacesheep@latest live push --space <link> --status "Fetching the Design skill"` (no space yet: skip it). fold.js's first status replaces it. Read a reference only at the step that names it.

## Order of work

`<folder>` below is the folder you build in (it gets `work/` and `draw/`). You run two commands and no other, written in full in every call: `node <this skill's folder>/assets/fold.js -C <folder> <step>`, short `fold.js <step>` below, which talks to the one space it started with through the spacesheep CLI (its header lists each step), and `node <this skill's folder>/assets/check.js -C <folder>`, short `check.js`, which only reads. Read and search files with Read, Grep and Glob (never `cat`, `sed`, `awk` or `grep` in a command), and make and change them with Write and Edit: a new file is one Write call, a change one Edit call. Never `$(`, backticks, a heredoc, `sed`, or page text passed through a command: a permission check can't read them, and a person can't see what they allow.

1. **Start at once.** Before any command, say: "To draw this quickly I need three things from you, once: allow two commands (`fold.js`, which writes the page to your space, saves versions and takes pictures through the spacesheep CLI, downloading that CLI from npm if it isn't installed, and keeps a writer running in the background until the design is saved or five minutes after work stops; and `check.js`, which only reads the files here), and let me edit files in this folder without asking each time. After that it runs by itself. If you'd rather approve each step, say so and I'll go slower." Then, with the link the person gave, `fold.js start <link>` (without this skill's folder, fetch `assets/fold.js`, `assets/check.js` and `assets/base.html` first). It reads the space into `work` while it puts up a status (the starter instead, if its page is blank: nothing on it yet but the platform's own marks, and then its empty canvas goes up the moment the read is back) and keeps its id. With no space yet, `fold.js start --new "<working title>"`. If section 1 says to ask, ask now (references/questions.md) and end the turn; on the answers, go on at step 2, the answers part of the brief.
2. **Push the frame within 90 seconds, with its helpers drawing,** having read only references/directions.md. From the brief alone, set each direction's slug, name, line and tokens in `work/index.html` with Edit calls in one message: the directions' tokens, and each section's opening tag (section 2 says how many): names and slugs are fixed from here. Leave every `<!-- part:… -->` placeholder as it is (fold.js names it after its section): the directions are drawn as parts (steps 3 and 4), each with its own status, so the person sees the build move. One design keeps the starter too, with one section: never Write `work/index.html` whole, since its head holds the kit, the switcher and the script the save's layout check runs. With helpers you can start (subagents, parallel tasks), start one per direction in that same message, after the Edits: the helpers, below. They only write parts, which the writer folds in when it starts. Push it, `fold.js push`, save it (`fold.js save "Frame" "Drawing three directions"`), and say in chat: "Three directions on the way: Harbour Chart, Night Watch, Logbook. Say if one is wrong.", adding "Dark too, or light only?" when section 1 finds dark unclear. **The title is the person's:** `fold.js start` keeps the space's own in the page; never change it unasked. Only when it clearly doesn't fit the work (Untitled, or a space called Q3 budget asked for a flyer), ask once, at the end of your last reply (section 6), and on their pick run `fold.js title "<their pick>"`. If an edit is refused, say in one line that you need edits allowed in this folder, and stop.
3. **Start the page's only writer:** `fold.js write`. It folds each direction's parts into `draw/frame.html` between its `<!-- part:<slug> -->` markers (fold.js names the starter's after their sections; add them where there are none), writes `work/index.html` and pushes the page and status within 2 seconds of a change. It stops at `fold.js stop`, or by itself five minutes after the last change (so a closed session leaves it at most five minutes), and `fold.js write` starts it again. From now on nobody else pushes or edits `work/index.html`: change the frame, tokens included, in `draw/frame.html`. A part is one Write call, `draw/night-watch/01.html`, then `02.html` and on, its first line its status: `<!-- status: Night Watch: prices -->`.
4. **Draw at once.** The helpers have been drawing since step 2. Without them, write every direction's top yourself as its first part (`draw/<slug>/01.html`, step 3), from the brief, before any long thought; then read (step 5); then the rest as the next parts, thought through once and sent as Write calls in one message with no checks between them, each direction top down. Never draw a direction in `work/index.html`: only parts carry a status the person sees. A helper that comes back refused or with no part: say once, "Helpers can't write here without your OK; drawing the directions myself", draw its direction yourself that way, and start no helper again. A part goes inside its direction's section, takes at most 45 seconds of writing, and every id in it starts with the slug.
5. **Read in one message while the tops go up,** with one status ("Reading Spark"): a Glob for the logo and the theme or layout files, a Grep for the nav labels and colour tokens, then Read on the two or three files they point to and one screen's worth of real rows. Use those tools, not `cd`, `ls`, `grep`, `cat` or `sed` in a command: each shell read is one more question for a person who approves each step. Stop when you have them. Put the tokens, and the logo once as a class every direction uses, in `draw/frame.html` with Edit calls: the next fold carries them everywhere.
6. **Finish the moment the last helper is back.** Start the save, `fold.js save "Three directions" "All three are up. Checking details" pictures`, then run `check.js` (section 5). Then `fold.js wait`: it prints how the save ended (run it again if it says still saving) and each layout fault measured on the saved page, which is a failure like the check's. When its last line starts `layout check failed`, fix each fault once with the rest, then stop: never save again for a fault. Look at every picture (`<folder>/<slug>-1440.png` and `<slug>-390.png`, each the whole direction, and a view's one at its width, `<slug>-phone-390.png`) in one message (section 5's look). Read the part files to fix in one message, then send the check's fixes and yours as Edit calls in one message: the writer folds them in. Then `fold.js stop "Three directions"`: it lets the last edits fold, stops the writer and saves. With nothing to fix, `stop` alone: it saves nothing and takes the work card down, so open tabs stop saying the page is being worked on. Then reply, that version in your first line: no second look. Say nothing final while a helper draws, a save runs, or the check lists a failure you don't name. If the save failed, stopped, is incomplete or misses a picture (its last line says which), fix what it names and run that save again. If it starts `save refused`, nothing was saved and saving again can't help: tell the person in one line why, and stop. If `wait` or `stop` says pushes were refused, tell the person in one line that the page isn't reaching their space. No local browser, Playwright, local server or build script.

**The save**, for the frame and the finish, never one per part: `fold.js save "<message>" "<status>"` saves a version in the background, puts the status straight back and pushes the newest page again. With `pictures` last, it also takes each whole direction at 1440 and 390 px wide (a view once, at its frame's width), and the page measures itself for text squeezed into a thin column, words past an edge and words cut off.

**The helpers**, one per direction, all started in the frame's message after its Edits (step 2), each at `low` effort where your client lets you (Claude Code's `effort`):

1. **These few lines each, and nothing more: the rest is in references/helper.md.** "You draw Night Watch (`night-watch`): <its line and idea>. The facts: <every fact in the request>. The words, the same in every direction: <the headline, its line and each item's words, written once>. Their answers: <each choice line, if any>. Must hold in every direction, in the person's words: "<each requirement they stated>". The skill's folder is `<this skill's folder>` and you build in `<folder>`. In one message, Read `<this skill's folder>/references/helper.md` and sections 3 and 4 of `<this skill's folder>/SKILL.md` with your Read tool, then do what helper.md says." Say in chat that the three are being drawn at once.
2. **While they draw, read (step 5) and write the brief:** what you read, and what each direction is for. Write it to `draw/BRIEF.md` with `ask: <the request word for word>` first, a line `fact: …` per fact, `choice: <question>: <answer>` per answer, `not: …` for words no direction may show (the admin's own menu, when the person wants it separate), a line `control: <name> (<token>) <kind>: <its values in order>` per control (section 3), such as `control: Leads with (--leads) choice: Prices | Booking | Workshop`, and `<!-- end brief -->` last. Put the same controls in the frame's Tweaks pane, `draw/frame.html`, with one Edit.

## What good looks like

- **It is the thing, not a picture of it.** Every button, tab and link does something. A prototype can be tapped through on a phone.
- **The brand is exact.** The colours, fonts, logo and tone come from what the person gave you, not from your taste. When they gave nothing, the look is a deliberate choice you name in one line.
- **Directions really differ.** Three directions differ in layout, type and colour, not in shades of one idea.
- **Every fact survives.** Each name, price, time, item and claim in the request appears in the design, spelled as given.
- **It looks chosen, not generated.** Nothing a template would add by habit.

When readability and style pull apart, choose in this order: readable and accessible, easy to use, a clear hierarchy, then style, then decoration.

## Never

- Never use placeholder text ("Lorem ipsum", "Your headline here", "$XX") unless the person asked for a wireframe.
- Never add stock photos, hotlinked images, web fonts from a CDN, or scripts from another host. The space must work offline and on paper.
- Never invent brand values when the person gave some. Never swap their logo for a wordmark you drew.
- Never put `data-ss-id` on a button, link, input or label. It goes on the readable block around it.
- Never change what the person didn't ask to change during a revision. That covers words, order, spacing, other directions and the ids.
- Never fall back on the look that reads as machine-made, unless the brand or the person asks for it: a cream, beige or peach page by default; purple or blue-to-pink gradients, or a gradient on every surface; a stock UI sans (Inter, Roboto, Arial, plain `system-ui`) for headlines; rounded cards with a coloured left border; an icon beside every heading; emoji as icons; blobs, orbs and glows; people or scenes drawn in SVG.
- Never invent evidence: numbers, ratings, testimonials, customer logos, awards or press quotes the person didn't give. Leave that part out and say in your reply what would fill it.
- Never promise what Spacesheep can't do: dragging boxes on a canvas, PowerPoint or Google Slides export, Figma import, or saving a brand for them. Say what to do instead (references/after.md, "Limits").
- Never make a version any way but `fold.js save` or `fold.js stop`: no `create_version`, `deploy` or upload of your own, even when a refusal suggests one. It skips the pictures and the layout check.

## 1. Read the brief

The frame goes up from the request alone (step 2); the rest is read after it (step 5).

1. **The request, word for word.** List every fact it gives (names, prices, hours, items, screens, steps); each one must appear in the design. List every constraint too, such as "on a phone", "one A4 page", "clickable" or "three directions", and every requirement in the person's own words ("clearly separate from the standard organization view"): each direction keeps them all, whatever its idea.
2. **The brand.** Use the first of these that exists:
   1. A design system block in your instructions. It wins: its colours, fonts, corners and tone override the defaults.
   2. A brand sheet, logo or colours the person gave in this conversation, or already in the space's source. Read references/brand.md before using one.
   3. A space of theirs they point to ("like our homepage"), if you can read it.
   4. Nothing. Choose a look on purpose and say which and why in your reply. Set it from who it's for, on four dials: colour mood, type character, density and decoration. A plumber's page is plain, sturdy and quick to scan; a wine bar is dark, fine and spare; a kids' swim club is bright and rounded.
   If they said "our brand" and none of these exist, ask once which they mean, and build in a neutral look meanwhile.
   Dark mode: clearly wanted (they said dark, or the brand's ground is dark), build every direction dark. Unclear: they never said dark, but it is mostly used after dark (a bar, restaurant or venue whose hours run into the evening or night; a product used late or in dim light, such as a night-shift tool), or its logo is dark. Then always ask, in step 2's chat line ("Dark too, or light only?"), and don't wait: build light meanwhile, and make dark a revision on a yes. No sign: light only.
3. **The space as it is now.** A redesign starts from the space's source, not the starter: it keeps every word, link, form and `data-ss-id` unless the person asked for new ones.
4. **The kind of design:** a one-pager or landing page, a clickable prototype, something for paper, a deck, or a set of components. Each has a part in section 4.
5. **A big brief** (a whole app, a site of many pages, a dashboard of many tabs) is narrowed to its one most important screen, drawn in full; name what you left out in your reply. A clickable prototype the person asked for keeps its screens.

**Ask once, before drawing,** only when the brief is new or vague and the answers would change the result. Ask nothing for a full brief, a revision or follow-up, or a small change; when the person said to just go, not to ask or not to wait; or when no answer can reach you (no question tool and no chat that answers, as in `claude -p`). Then make your best guesses, build, and name them in your reply. At most 4 questions with 2 to 4 choices each, your pick first (a chat form's `pick`; elsewhere labelled "<choice> (my pick)"), and `other: true` where a free answer helps. The form, where it goes and the answers: references/questions.md.

## 2. One design or three directions

- **Make three directions** when the person asks for options, directions, "a few", "some ideas" or "different looks". Make three as well when the look is the point and still open: a one-pager, landing page, poster, flyer or notice in a new space, with no brand given and no style named. "One page" or "one A4 sheet" is its size, not how many designs. When they name a number, use it, from 2 to 5: more than 5 dilutes each one, so offer 5 and say why.
- **Make one design** when the brand and content are fixed and the person asked for one thing ("make a one-pager in our brand"), and for a prototype, a deck or a component sheet unless they ask for options.
- **All the directions sit in one space,** in one row on the canvas (each later round adds a row below: section 7), in the canvas area under the switcher: `assets/base.html` has both. Each direction is a `<section class="direction" data-ss-section data-ss-id="direction-<slug>" data-ss-thing="direction/<slug>">`. The `data-ss-thing` keeps comments on a direction while another shows. A link ending in `#direction-<slug>` opens that direction, and in a chat reply a button opens one with `{"emit": {"name": "show-direction", "data": {"id": "direction-<slug>"}}}`.
- **Phone and tablet views are frames you build.** Spacesheep has no size switch: a phone or tablet design is a frame on the canvas, drawn for that width. Each direction is one desktop frame (1280 × 800). Add a view only when the person asks ("the phone version", "responsive", "and on mobile"), for the directions they name, and to every direction only when they say so: never by default, since each view is a design of its own. A design only for phones (an app's screens) is made of phone frames from the start (references/prototypes.md), not views.
  - **Its place:** a section of its own after the last direction's, drawn under its own direction on the canvas: `<section class="direction" data-view-of="<slug>" data-ss-frame="phone" data-ss-section data-ss-id="direction-<slug>-phone" data-ss-thing="direction/<slug>/phone" data-ss-label="<Name> · Phone" data-ss-x="<its direction's x>" data-ss-y="896">`. A tablet view is the same with `tablet` (820 wide); with both, the tablet goes first and the phone at x + 892. Views come after every direction, in the directions' order, because the canvas numbers frames in page order: the directions keep 1 to n, their number keys and the switcher's tabs match, and the views take the numbers after. The switcher keeps one tab per direction; on the canvas a direction's number key, pressed again, steps through its views and back.
  - **Its look:** its ids start `<slug>-phone-`, and the direction's token rule lists it beside the direction, `[data-ss-id="direction-<slug>"], [data-view-of="<slug>"] { … }`, as does any of the direction's CSS it shares.
  - **Drawn for its width:** every fact, word, brand value and control of its direction, arranged for a hand: one column, the main action within a thumb's reach, the nav folded into the kit's bar. Never the desktop frame copied or scaled down.
  - **In a new build,** add each view's section in the frame's Edits (step 2) with its own empty `<!-- part:<slug>-phone --><!-- /part:<slug>-phone -->`, and name it in its direction's helper prompt ("Its phone view: `night-watch-phone`"). On a page without the canvas (the client copy), the switcher shows Desktop / Phone buttons for a direction with views, and a phone opens on the phone view.
- **Each has an about block:** references/directions.md, "About blocks".
- **Name each direction by its idea** in 1 to 3 words ("Harbour Chart", "Night Watch", "Logbook"), never "Option A". Its line says what it is for and what it gives up ("Calm and plain, for owners who check once a month; no totals at a glance").
- **When the person picks one** ("go with the third", "the third, but bolder", or "Use Harbour Chart" from its ⋯ menu or the bar), change only that direction, mark it chosen (`data-chosen` on its section, and on no other), make it the one the space opens on (`data-default`), point the canvas at it (`fold.js focus <slug>`), and record the pick under Decisions (section 6). A pick from a pill carries no reason: in that reply, ask once, in words and not as a form, what made them pick it, add their answer to its Decisions line if one comes, and never hold anything for it. Keep the others, so they can still compare or come back. Remove them only when the person says so ("drop the others", "just that one").

## 3. Build it so it works

- **The starter carries the frame.** In `assets/base.html` the `ss-chat` meta puts chat beside the design (`content="open session"` when you are the person's own session, so their replies come back to you), and `<div data-ss-canvas-area>` lays the directions in it side by side with pan, zoom and Fit. Add no canvas, camera or controls of your own: Comment, Edit and versions are Spacesheep's. The starter's top bar is the frame: Back while a direction is open full page (Esc too), the tabs, Tweaks and Export (PDFs, HTML, a build prompt). Each card has a ⋯ menu on its label row, and the bar with a direction open has the same two: Use this and Another round say "Use <name>" and "Another round of <name>" in the chat as the person (fold.js names each section's menu with its part). Keep them as they are, the menu first in its section, and write no back, zoom, reload, pick, menu or download button of your own.
- **Screens on the canvas.** Mark each screen `data-ss-frame="phone"`, `tablet`, `desktop` or a size such as `800x600`, with a `data-ss-label`, and place it with `data-ss-x` and `data-ss-y` if you need to. Every screen stays visible: never hide one, nor set overflow or height on its section.
- **Build from the kit, phone first.** The starter's parts finish their own alignment, wrapping and spacing at 390 and 1440 px: `.k-bar` (logo, nav, `.k-back`), `.k-hero` with `.k-actions`, `.k-cards` of `.k-card` (the last row always fills), `.k-table` (`data-label` on each cell, `.num` for numbers), `.k-stats` of `.k-stat`, `.k-chips` of `.k-chip`, `.k-btn` (`.line`, `.quiet`), `.k-search` (a label, and a placeholder of at most 20 characters), `.k-tabs`, `.k-filters` with a `.k-filters-toggle` button, `.k-steps` (`data-state="done"` or `"skipped"`, `aria-current="step"`) with `.k-steps-count`, `.k-empty` (the only "nothing here"), `.k-label` and `.k-meta`. Arrange them your direction's own way and restyle them freely, but never rebuild one, and add no shelf, scroller or width of your own. Tap targets are at least 44 px, body text at least 16 px. Each frame lays out at its own width, not the window's: the kit's phone rules are container queries on the frame, so write yours as `@container (min-width: …)`, never `@media`, and sizes in `cqi`, never `vw`.
- **One self-contained document.** Draw the logo as inline SVG (paste the one they gave you). Write icons as inline SVG from one family, coloured with `currentColor`, and only where they help someone find or tap something. Carry the design with type, colour, shape and the real content. Use system font stacks close to the brand font; add an `@font-face` with a data URI only when the person gave you the font file.
- **Tokens first.** Every brand value is a CSS variable named for its role. Colour comes in pairs, a surface and the text on it: `--brand-ground` and `--brand-ink`, `--brand-surface` and `--brand-on-surface`, `--brand-accent` and `--brand-on-accent`, with `--brand-muted` for quiet text; every pair reads at 4.5:1, and check.js measures them. Shape and rhythm: `--radius`, `--density`, `--rule`, `--shadow`, `--label-case`, `--label-track`, `--display-weight`, `--font-display`, `--font-body`. Each direction sets its own on its section, as the starter does, so its parts look like it and a change to one never touches the others.
- **Controls from this design.** Up to 6 things this person will likely want to flip without asking you, each an input in the starter's Tweaks pane, `<label>Name <input …></label>`, as its comment shows; the bar's Tweaks button opens them. At least two are a switch or a choice about this brief, and your questions are the best source: the answers not picked become the other values ("Leads with: Prices / Booking / Workshop", "Main button: Book / Call / Find us", "Opening hours: on / off"). The accent and spacing (`--density`) may sit beside them; corners only where a direction's look turns on them. Every direction answers every control: it sets each control's token on its own section, so it opens as designed, and a switch or choice marks the section `data-<token name>="<value>"`, so style every value but the one it opens on, as in `[data-ss-id="direction-<slug>"][data-leads="2"]`. A choice has 2 to 4 options of at most 14 characters.
- **Type that reads as designed.** Pair a display face with a different, quieter body face; use one family only for dense tools and data. Set every size on the starter's scale. Body text has a line height of 1.5 to 1.7 and lines of 45 to 75 characters (`max-width: 68ch`). The starter's three directions show display stacks with character. A display stack must look right in every face it names, not only the first: many screens, and the save's pictures, lack the first face, and a taller one can push tight type into the text beside it. Display type set under line-height 1 keeps its line-height and gets a margin of a fifth of its size above and below.
- **One place for the eye.** Each screen has one thing seen first, then a second and a third level. Make the levels with size, weight, colour and space, not with boxes, borders and cards.
- **One accent, one bold move.** The accent shows at most twice on a screen: the main action and one highlight. Give the design one decisive move, such as a huge headline, one dark field or one striking number, and keep the rest quiet.
- **Real content only.** Use the person's words and facts, and name the product the design sits in on every direction (a page inside Spark says Spark). Where the request lacks something a real design needs, write plausible, specific wording and flag it in your reply ("I wrote the doors-open time as 6:30 pm: please check").
- **Everything clickable does something.** A link goes to a section, another screen or a real address. A button changes the state, opens what it names, or, in a mockup, shows a short line saying what it would do. Never leave a dead `href="#"`.
- **Commentable.** Every readable block has a unique, descriptive `data-ss-id` with its direction's prefix (`chart-hero`, `nightwatch-prices`). Every top-level section has `data-ss-section`. Ids stay stable from version to version.
- **Accessible.** Use real `<button>` and `<a>` elements, labels on inputs, visible focus styles, and `prefers-reduced-motion` to switch movement off.

## 4. Each kind of design

**One-pager or landing page.** One clear message at the top, the facts in the order a visitor needs them, and one main action, repeated at the end. Lead with the thing (the product, the menu, the timetable), not a slogan about it. Only one solid main button shows on a screen. Don't default to a hero, three feature cards, pricing and an FAQ: make one part something only this offer could have, such as its real price list as the hero.

**Clickable prototype.** Read references/prototypes.md first. Each screen is a section, and links and buttons move between screens inside the one space. State such as choices, limits and the selected item lives in a small inline script, so what the person taps works ("up to four passengers" refuses a fifth).

**Paper (a flyer, poster, menu or "one A4 page").** Nothing hidden behind motion or a click, no blurred shadows, fonts the server has. Add `@page { size: A4; margin: 12mm }` (or the size they name). Write no `@media print` rules: the platform adds them. Inside 12 mm margins an A4 sheet is about 700 × 1,030 px, and "one page" means it fits: shorten the copy or tighten the spacing, never text below 9 pt.

**Deck.** Follow the house presentation rules for slides. With directions, show a title slide and one content slide in each, then the full deck in the one they pick.

**Components or a style sheet.** Show each component in each of its states (default, hover or focus, disabled, error, empty), labelled, with the tokens table at the top.

**Motion.** CSS transitions and keyframes timed with `--ease` and `--dur`, only where they explain something: entrances, a state change, progress.

## 5. Checks, once it's visible

**The source checks are `check.js`'s:** the brief's facts and not-lines, six words quoted from the request or a direction's line, ids, links, handlers, scripts that parse and can run again after a push, widths on a phone, placeholders, colours from the tokens, type size and page size. It prints each failure with its file, line and fix, or "all pass". Never write a check script of your own.

**The look is yours,** once per direction on its picture at the finish (order of work, step 6):

1. **Requirements.** It shows every requirement the person stated, without quoting one.
2. **Brand.** The fonts are the brand's or the stack you named, and the logo is theirs, unchanged. references/brand.md has the full check.
3. **Contrast.** Text passes AA: 4.5:1, or 3:1 at 24 px and larger, in hover, focus and selected states too. Change the background or border, never fade the text, and show a `:focus-visible` ring.
4. **Paper, when asked.** It fits the sheet, and nothing needed depends on motion or is hidden.
5. **Score.** From 1 to 5 on fit (made for this brief, or your usual default? Its idea shows in the layout, not only the colours: a stock card grid in new colours is a 2), hierarchy (one place for the eye?), finish (type, spacing and alignment exact?), specificity (could it belong to anyone else?) and restraint (one accent, one bold move, nothing from Never). Fix anything under 3. Then confirm in the picture: nothing cut off at an edge, no text on other text, no empty tile or band that looks like content, no card alone on a row.

## 6. Say what you made

Reply in at most five short lines, then, only when step 2 found the title doesn't fit, the rename question as its last thing (references/questions.md, "Rename"):

- what you made and its saved version (one design, or three directions by name),
- the guesses you took (the brand source, any copy you wrote, anything you left out) and what is still rough,
- how to give feedback: tap a block and comment with @shepherd in it, or say it in this chat,
- the next step: with directions, one decision line ("If you want the due dates first, pick Harbour Chart; every bill at once, Logbook"); else approve it or hand it to a developer.

**Keep a Decisions log on the space.** After the first revision or decision, add it at the very end: `<details class="no-print" data-ss-id="decisions" data-ss-canvas="pin" style="display:none"><summary>Decisions</summary>…</details>`, one line per decision with the date, version and the person's reason when they gave one ("11 Nov, v4: picked Night Watch, for the due dates first; bolder type"). Before new work in a space, read its log in `work/index.html` and start from the taste it records. It is the record, read from the source, never shown: the canvas draws any block outside a direction as a frame of its own, so `data-ss-canvas="pin"` keeps it off the canvas, and the check flags a log that would show.

## 7. Revise from comments and chat

- **A request can come from the chat or from a comment that asks Shepherd** (it mentions @shepherd, or the person tapped Send to Shepherd). A comment is pinned to a block, and that block is the target: change only what it names.
- **Say what you'll change, then read the current source,** in one command and before anything else: `fold.js read "<what you'll change>"` ("Making Big Day's 18 red") puts that status on the page within seconds, then reads. In a folder with no space yet, `fold.js start <link> "<what you'll change>"` does both. The person may have changed words in Edit mode since your last version. Keep their edits.
- **Show it, then save it.** With that status up, make the smallest change on the block's `data-ss-id` in `work/index.html`, push the page (`fold.js push`), then save it (the save). The read put the last build's frame and parts aside, so the save sends the page as you edited it. Replace the whole document only for a redesign.
- **A change to what a control sets changes the control.** When the change moves a value a Tweak offers (a time, a price, a name), the option it opens on says the new value ("2pm" becomes "3pm"), the other options still read as choices beside it, and each one shows what its label says. Change the brief's `control:` line to match.
- **"Keep the layout" means nothing moves.** Change only token values, words or the one property named. A mood word ("calmer", "bolder") moves the matching tokens: hue and neutrals for colour, size and weight for type. Check contrast again.
- **The canvas follows the work.** The starter opens on every direction (`<meta name="ss-canvas-focus" content="all">`). When the person picks a direction or asks for a change to one, run `fold.js focus <slug>` before you push the change, so the canvas opens that direction large. When they ask for alternatives again, or a new direction is added beside it, run `fold.js focus all`. A person's own choice in their tab holds until the focus changes again.
- **"Show me the phone version of Harbour Chart"** adds a view (section 2) and changes nothing in the desktop frame. `fold.js read "Drawing Harbour Chart for a phone"`, then `fold.js kit` (it brings a page made before views up to the starter's switcher, Export, container rules and layout check, or says it is current). An older page without Export: `fold.js kit` adds it. Add the view's section after the last direction's with one Edit and its token selector with another, run `fold.js focus <slug>-phone`, push, then save with `pictures` and look at `<slug>-phone-390.png`.
- **Several asks:** make and push them one at a time, then save once.
- **"Keep these for Night Watch: …"** (from Tweaks, or pasted) lists the values the person settled on: write them into that direction's tokens in `work/index.html`, delete those tokens' rules from `<style data-ss-id="ss-style">`, and change nothing else.
- **Close the loop.** On a turn started from a comment, your reply is posted under it and you can't resolve it: say what changed in one line. On a chat turn, resolve each comment your change answered.
- **Every change is a version,** so history reads as a changelog. "Undo that" restores the earlier values in a new version.
- **More versions are a new round, on the same canvas** ("more like Night Watch", "Another round of Night Watch" from its menu, "two versions of the third, one bolder", "try it lighter"). A direction's own space only when asked in words: `fold.js copy night-watch` puts it alone in a new private space named after it; give them the link. Three versions, or the number they name (1 to 5), of the direction they name, else of the chosen one; with neither, ask which. `fold.js read "Drawing three versions of Night Watch"`, then `fold.js round night-watch "<Name>" "<Name>" "<Name>"`, each named for what it changes in 1 to 3 words. It adds each version after the last direction, as a direction with its parent's frame and tokens, a pill and an empty part, in a row of its own below everything, joined to its parent by a line, and points the canvas at every direction. Then build them as from step 2: each version's `data-line` (what it changes from its parent, and what that gives up) and the tokens it changes, with Edits in `work/index.html`; push; save ("Round 2", "Drawing three versions of Night Watch"); `fold.js write`; one helper per version, given its parent's section to start from and what to change; then step 6. Earlier rounds stay as they are, their comments with them: never move, redraw or remove one unasked.

## 8. After the build

For client approval, a hand-off to a developer, saving a look as a brand, or anything Spacesheep can't do (PowerPoint, Figma, dragging boxes), read references/after.md first.

## Worked examples

**"Brand sheet and logo attached. We need a flyer for Harbour Lane Library's winter talks: a title, four talks with dates and speakers, the address and a book-a-seat button. People will read it on a phone, and we'll pin it up printed on one A4 page."**
One design, because the brand and content are fixed. Push the frame at once, then read the brand sheet (references/brand.md) and push the shared look: its tokens and the logo inline. Draw top down: the title block, the four talks with the date first, the address, the button. Add `@page { size: A4; margin: 12mm }`. Save it, look at its picture, and check: 4 talks, every colour a token, one A4 sheet. Reply: "Flyer in your brand. I wrote the title as 'Winter talks at Harbour Lane'. Comment on any block with @shepherd to change it."

**The comment "@shepherd just the date and the title, and make the dates our navy", pinned on the talks list.**
Edit only inside `talks`: cut each talk to its date and title, keeping every id, and set the dates to `var(--brand-ink)`. Check the contrast, push, save, and reply in one line with both changes.

**"We need a landing page for Tidewell, an app that tells small-boat owners when their mooring fees are due and lets them pay from a phone. It's £6 a month, and the first month is free. Give me three directions I can flick between."**
The frame is up within 90 seconds, its three directions named in chat. Helpers draw the three at once, each top first and with every fact (due-date reminders, paying from a phone, £6 a month, first month free). Then one save with the three pictures, one look at each, one round of fixes.
Then "The third one, but bolder. Don't touch the words." Change only the type and colour tokens on the third direction's section, check its contrast, make it the default, and add a line to Decisions.
